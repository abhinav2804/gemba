# Gemba: architecture (v0.1)

One container, one URL. Simple to deploy on Cloud Run, simple to demo, honest to explain.

```
Browser (no build step: ES modules, Three.js from a CDN import map)
  Control room ─ 3D twin ─ KPI strip ─ Gemba cards        ◄── SSE /api/stream   (plant ticks)
  Gemba Walk   ─ 6 agent lanes, tool calls as they happen ◄── SSE /api/walk     (agent events)
  Ask Gemba    ─ chat, answers with charts and sources    ──► POST /api/ask
  Quality      ─ camera / upload → boxes + defect class   ──► POST /api/inspect
  Machine 360  ─ sensors, health, time to failure, spares ──► GET  /api/machines/{id}
  Work orders  ─ approve with a name, audit log           ──► POST /api/orders/{id}/approve
  Worker phone ─ job card, lock-out, voice Q&A            ──► POST /api/voice
         │
Cloud Run service `gemba` (Python 3.12, FastAPI, uvicorn)
  sim/        plant model: 3 plants, lines, machines, sensors, production, quality, energy, orders, stock;
              scenario engine (inject faults, jump time, reset), deterministic seed
  analytics/  features, anomaly (IsolationForest), time-to-failure range (trend to trip limit), SPC,
              demand forecast (exponential smoothing), energy baseline (kWh per good part), OEE
  data/       DuckDB views over the live state (telemetry, events, quality, energy, orders, stock, work orders)
              for NL-to-SQL; read-only, row-limited, allow-listed tables
  agents/     llm.py   one client, three providers: vertex (Cloud Run, ADC) | gateway (llm.lehana.in, local) | mock
              tools.py typed tools the agents call (query_sql, machine_detail, forecast, stock, schedule, what_if…)
              walk.py  Gemba Lead + 5 specialists, parallel, streamed events, schema-validated Gemba cards
  store/      work orders, approvals, audit log (memory now; Firestore on GCP)
  static/     the web app
         │
Gemini on the Gemini Enterprise Agent Platform (formerly Vertex AI) from Cloud Run; llm.lehana.in locally
  agents: gemini-3.8-flash for the five specialists; gemini-4-argon (GA 13 Oct 2026) for the Lead's root cause and plan
  voice:  push-to-talk audio → Gemini (structured answer); Gemini 3.8 Live as the stretch (no structured output there)
  vision: image understanding with bounding boxes · audio: speech in, answer in the same language · TTS (stretch)
```

Names follow the 22 Apr 2026 rename: Vertex AI → Agent Platform, Agent Engine → Agent Runtime, Vertex AI Studio →
Agent Studio (research: `docs/research/01-deep-research.md` finding 3). Reference pattern judges will recognise: edge
connectivity → Manufacturing Data Engine → BigQuery → Gemini agents; our simulator stands in for the edge.

## Key decisions

| Decision | Choice | Why |
|---|---|---|
| Hosting | One Cloud Run service (FastAPI serves API + static app) | Required by the rules; one URL; scales to zero; streaming (SSE) works |
| Frontend | Vanilla ES modules + Three.js (import map), our own charts in SVG/canvas | No build step, fast to iterate, full control of the look; fresh code |
| Live updates | Server-Sent Events | One-way streams are all we need; works on Cloud Run |
| Agents | Our own orchestrator on Gemini function calling (ADK-shaped: root agent + sub-agents + tools) | Full control and visibility of every step for the "watch the walk" UI; ADK port is a stretch |
| Gemini access | `vertex` provider on Cloud Run (service account, no keys); `gateway` provider locally | Rules want Google AI; platform rule wants the gateway; both behind one interface |
| Data | In-memory simulator + DuckDB SQL views | Zero ops, fast, real SQL for NL-to-SQL; BigQuery is the scale-out story |
| State | Memory (demo resets on cold start) → Firestore when the GCP project exists | Approvals survive restarts on GCP |
| ML | scikit-learn IsolationForest + physics trend; no deep learning | Explainable, trains in seconds at startup on synthetic history |
| Images | Generated by us (procedural + optionally Gemini image model), never third-party datasets | Rule R5 |

## Agent contract

- Every agent gets: a role prompt, the tools it may call, the plant snapshot summary, and a strict output schema.
- Tool results are data the agent cites; the final card lists `evidence` (tool name + key numbers).
- The Lead receives the five findings and returns `GembaPlan { headline, links[], cards[], tradeoffs, do_nothing_cost }`.
- Server validates JSON; on failure it retries once with the validation error, then falls back to the rules engine and
  labels the card "rules fallback".
- Events streamed to the UI: `agent_start`, `tool_call`, `tool_result`, `finding`, `link`, `plan`, `agent_error`.

## Security and safety

- No secrets in git. Local: gateway key read from `/root/.secrets/...` at runtime. GCP: service account (ADC), Secret
  Manager if a key is ever needed.
- NL-to-SQL: read-only DuckDB connection, allow-listed views, `LIMIT` enforced, single statement, 2 s timeout.
- Approvals need a name; the audit log is append-only.
